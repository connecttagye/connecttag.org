لماذا تتباطأ بعض واجهات Jetpack Compose أثناء التمرير؟ الدليل الهندسي لإتقان Recomposition، استقرار الأنواع (Stability)، وBaseline Profiles

تاريخ النشر: 08 نوفمبر 2026

على شاشات الهواتف الحديثة التي تعمل بمعدل تحديث 120Hz، لا يملك محرك الرسم سوى 8.33 ملي ثانية فقط لإنجاز حسابات وإظهار كل إطار بصري (Frame). وعندما يتجاوز تنفيذ إحدى دوال @Composable هذا الهامش الزمني الضيق بسبب إعادة تركيب جماعية غير ضرورية (Unnecessary Recomposition)، يشعر المستخدم فوراً بتقطيع وتلكؤ أثناء تمرير القوائم الطويلة (Jank / Dropped Frames).

استكمالاً لما طرحناه في الدليل الشامل لـ Jetpack Compose والدليل الهندسي لمعمارية MVI وإدارة الحالة التفاعلية، نغوص في هذا المرجع الهندسي في آلية عمل مترجم Compose (Compose Compiler) من الداخل: كيف يقرر ما إذا كانت الدالة قابلة للتخطي الذكي (Smart Skipping)، ولماذا تفشل القوائم القياسية List<T> في اختبار الاستقرار، ومتى تستخدم derivedStateOf بدلاً من remember، وكيف نوظف مكاتب mvi-lib-kmp وcommon-models وtheme-effects-compose في قسم المكاتب البرمجية في كونكت تاق لضمان أداء ثابت بسرعة 120 إطاراً في الثانية.

خلاصة تنفيذية سريعة (Key Takeaways)
  • التخطي الذكي (Smart Recomposition) يعتمد على استقرار المدخلات: لا يستطيع Compose تخطي إعادة تشغيل دالة @Composable إلا إذا كانت جميع معاملاتها مستقرة (Stable) ولم تتغير قيمها مقارنةً بالإطار السابق.
  • واجهة List<T> غير مستقرة افتراضياً: لأن List في كوتلن قد تشير في وقت التشغيل إلى ArrayList قابلة للتعديل، يعيد المترجم رسم أي مكون يستقبلها دائماً؛ والحل هو استخدام ImmutableList أو وسم الكلاس بـ @Immutable أو تفعيل Strong Skipping Mode.
  • أجّل قراءة الحالة إلى مرحلة التخطيط أو الرسم: تمرير الحالة المتغيرة باستمرار (مثل إزاحة التمرير أو الشفافية) داخل دالة لامدا Modifier.offset { ... } أو Modifier.graphicsLayer { ... } يتخطى مرحلة التركيب (Composition) بالكامل!
  • مفتاح key في LazyColumn إلزامي: غياب key = { item.id } في القوائم الديناميكية يجبر Compose على إعادة بناء كافة العناصر عند إضافة أو حذف عنصر واحد في أعلى القائمة.

1. مراحل الإطار الثلاث في Compose (Composition → Layout → Drawing) وتأجيل قراءة الحالة

لفهم سبب تباطؤ الواجهات وكيفية علاجه جذرياً، يجب أن تدرك أن كل إطار بصري في Jetpack Compose وCompose Multiplatform يمر بثلاث مراحل متتابعة باتجاه واحد:

المراحل الثلاث لرسم كل إطار في Jetpack Compose (The 3 Phases of a Frame)

1. مرحلة التركيب (Composition)
ماذا سنعرض؟ (What to show)

تنفيذ دوال @Composable وبناء شجرة عقد الواجهة في جدول الفتحات (Slot Table). هي المرحلة الأعلى تكلفة على المعالج عند تكرارها كل إطار.

2. مرحلة التخطيط (Layout)
أين سنضع كل عنصر؟ (Where to place)

قياس أبعاد كل عقدة (Measure) وتحديد إحداثيات موقعها (X, Y) على الشاشة (Place) في مسحة واحدة سريعة (Single-Pass Measurement).

3. مرحلة الرسم (Drawing)
كيف نرسم البكسلات؟ (How to render)

إصدار أوامر الرسم المباشرة على لوحة Canvas (أو طبقة Skia/Impeller) لتحريك الألوان والظلال والشفافية بأقل عبء ممكن.

السر الهندسي الأول (تأجيل قراءة الحالة — Deferring State Reads): يتتبع نظام Snapshot System في Compose اللحظة التي تقرأ فيها قيمة متغير State<T>. إذا قرأت إزاحة التمرير أو قيمة التحريك مباشرةً كرقم داخل جسم الدالة Modifier.offset(y = scrollOffset.dp)، فإنك تجبر Compose على إعادة تنفيذ المرحلة الأولى (Composition) ثم الثانية ثم الثالثة في كل إطار! أما إذا مرّرت القراءة داخل دالة لامدا، فإن القراءة لا تحدث إلا في مرحلة التخطيط أو الرسم:

// ❌ Anti-Pattern: Reading state during Composition forces Recomposition on EVERY frame!
val scrollY by remember { derivedStateOf { listState.firstVisibleItemScrollOffset } }
Box(modifier = Modifier.offset(y = scrollY.dp))

// ✅ Engineering Best Practice: Defer state read to the Layout phase via Lambda Modifier
// Zero Recomposition! Only Layout & Draw phases run at 120fps.
Box(
    modifier = Modifier.offset {
        IntOffset(x = 0, y = listState.firstVisibleItemScrollOffset)
    }
)

// ✅ Defer alpha/scale/rotation to the Drawing phase via graphicsLayer {}
Box(
    modifier = Modifier.graphicsLayer {
        alpha = animatedAlphaState.value
        translationY = parallaxOffsetState.value
    }
)

2. كيف يعمل مترجم Compose؟ تشريح الاستقرار (Stability) و@Immutable وStrong Skipping

أثناء ترجمة الكود، يفحص مترجم Compose Compiler كل كلاس يتم تمريره كمعامل لدالة @Composable ويصنفه إلى فئتين:

  1. الأنواع المستقرة (Stable / Immutable Types): تشمل الأنواع الأولية (Int, Long, Boolean, Float, String)، ودوال اللامدا، والكلاسات البيانية (data class) التي تكون جميع خصائصها معرّفة بـ val ومن أنواع مستقرة. عندما تستقبل الدالة معاملات مستقرة فقط، يضع المترجم عليها وسم Skippable؛ أي إذا لم تتغير قيمة المعامل، يتخطى Compose إعادة رسمها تماماً.
  2. فخ المجموعات القياسية غير المستقرة (Unstable Collections Trap): إذا أضفت خاصية val items: List<Product> داخل كلاس الحالة، سيصنف المترجم الكلاس بالكامل على أنه غير مستقر (Unstable)! السبب هو أن List في كوتلن هي واجهة فقط، وقد يمرر المطور خلفها كائن ArrayList قابل للتعديل: 
    import androidx.compose.runtime.Immutable
import kotlinx.collections.immutable.ImmutableList
import kotlinx.collections.immutable.persistentListOf

// ✅ Solution 1: Annotate your UI State class with @Immutable (Contract with the compiler)
@Immutable
data class CatalogUiState(
    val isLoading: Boolean = false,
    val products: List<ProductItem> = emptyList(),
    val selectedCategory: String = "الكل"
)

// ✅ Solution 2: Use kotlinx.collections.immutable.ImmutableList for guaranteed immutability
data class OrderSummaryState(
    val lines: ImmutableList<OrderLine> = persistentListOf()
)
  3. وضع التخطي القوي (Strong Skipping Mode في Kotlin 2.0+): في الإصدارات الحديثة من مترجم Compose المدمج مع Kotlin K2، أصبح وضع Strong Skipping مفعلاً افتراضياً؛ حيث يقارن المترجم المعاملات غير المستقرة عبر مقارنة المرجع في الذاكرة (Referential Equality ===)، بينما يقارن المعاملات المستقرة عبر دالة المساواة البنيوية (Structural Equality .equals())، مع حفظ دوال اللامدا تلقائياً بـ remember.

3. جدول المقارنة الهندسية: متى تستخدم remember مقابل derivedStateOf والـ Lambda Modifiers؟

يخلط كثير من المطورين بين استخدام remember(key) وderivedStateOf. يوضح الجدول الهندسي التالي القاعدة الحاسمة لاختيار الأداة الصحيحة في كل سيناريو:

الأداة البرمجية متى تُستخدم هندسياً؟ مثال تطبيقي صحيح الخطأ الشائع الذي يجب تجنبه
remember(key1) { ... } حفظ نتيجة عملية حسابية مكلفة بحيث يُعاد حسابها فقط عندما يتغير key1 (تغير المدخل يساوي تغير المخرج). فلترة أو ترتيب قائمة منتجات عند تغير نص البحث أو القسم: remember(query, list) { list.filter(...) } تمرير متغير يتغير في كل إطار مثل listState.firstVisibleItemIndex كـ key.
remember { derivedStateOf { ... } } عندما تتغير الحالة المصدرية بتردد عالٍ جداً، بينما النتيجة المشتقة لا تتغير إلا نادراً. إظهار زر «العودة للأعلى» عندما يتجاوز التمرير العنصر الأول: derivedStateOf { listState.firstVisibleItemIndex > 0 } استخدامها لدمج متغيرين عاديين يتغيران بنفس وتيرة النتيجة (يُضيف عبئاً غير مبرر).
rememberUpdatedState(newValue) التقاط أحدث قيمة لمعامل أو دالة رد نداء (Callback) داخل LaunchedEffect(Unit) طويل الأمد دون إعادة تشغيله. شاشة بداية (Splash Timer) أو مستمع أحداث يستدعي onTimeout() المحدثة بعد انتهاء المؤقت. وضع دالة onEvent مباشرةً كمفتاح لـ LaunchedEffect مما يعيد تصفير المؤقت عند كل رسم.
Modifier.drawWithCache { ... } تخزين كائنات الرسم المكلفة مثل Path وBrush وShader مؤقتاً بحيث لا يُعاد إنشاؤها إلا إذا تغير حجم مساحة الرسم. رسم الخلفيات المتدرجة والتوهج الزجاجي والرسوم البيانية المخصصة بسرعة 120fps. إنشاء كائنات Paint() أو LinearGradient جديدة داخل drawBehind في كل إطار.

4. القواعد الذهبية لتسريع القوائم الطويلة (LazyColumn Keys & ContentType) وBaseline Profiles

تُعدّ القوائم الكسولة (LazyColumn وLazyVerticalGrid) المصدر الأول لمشاكل الأداء إذا أُهملت ثلاثة إعدادات جوهرية فيها:

  1. تحديد key فريد وثابت لكل عنصر: افتراضياً، يعتمد LazyColumn على موقع العنصر في القائمة (Index) كمعرّف له. فإذا أُضيف عنصر جديد في أعلى القائمة، تتغير أرقام مواقع كافة العناصر تحته، فيعيد Compose رسم الشاشة بالكامل! بينما بتمرير key = { item -> item.id }، يدرك المحرك أن العناصر القديمة تحركت للأسفل فقط دون أن تتغير بياناتها.
  2. تحديد contentType لإعادة تدوير العقد المتشابهة: عندما تحتوي القائمة على أنواع متعددة من البطاقات (مثلاً: عنوان قسم، بطاقة مقال، إعلان)، فإن تحديد contentType = { item -> item.viewType } يسمح لـ Compose بإعادة استخدام التراكيب المخزنة (Subcomposition Reuse) بين البطاقات من نفس النوع بكفاءة قصوى.
  3. توليد ملفات Baseline Profiles لتسريع الإقلاع والتمرير بنسبة 40%: أضف وحدة BaselineProfileGenerator إلى مشروعك لتوليد ملف baseline-prof.txt يُرفق تلقائياً داخل حزمة AAB، مما يتيح لنظام أندرويد ترجمة دوال Compose الحرجة مسبقاً (AOT) عند التثبيت دون انتظار التفسير الفوري (JIT).

5. التطبيق العملي عبر مكاتب كونكت تاق (mvi-lib-kmp وcommon-models وtheme-effects-compose)

لتجنيب فرق التطوير الوقوع في فخاخ عدم استقرار الحالة أو بطء رسم المؤثرات البصرية، صمم الفريق الهندسي في كونكت تاق مجموعة مكاتب قياسية مصممة بأعلى معايير الأداء:

مكاتب Compose وKMP عالية الأداء في كونكت تاق:

  • مكتبة common-models ومكتبة mvi-lib-kmp في قسم المكاتب البرمجية: توفر عقود UiState وCollectionResult الموسومة مسبقاً بمعايير الاستقرار الصارمة، مما يضمن تخطي إعادة الرسم (100% Skippable Composables) في كافة شاشات التطبيق.
  • مكتبة theme-effects-compose في قسم المكاتب البرمجية: محرك مؤثرات بصرية مبني بـ drawWithCache لتوليد التدرجات اللونية المتحركة (Mesh Gradients) والتوهج الزجاجي (Glassmorphism) في مرحلة الرسم مباشرةً دون التسبب في أي Recomposition.
  • خدمة تطوير تطبيقات الهواتف والأنظمة المتعددة: بناء وتحديث تطبيقات الأندرويد وCompose Multiplatform بأداء أصيل وتجربة استخدام فائقة السلاسة.

6. الأسئلة الشائعة والمصادر الهندسية المعتمدة

لماذا يعتبر مترجم Jetpack Compose قائمة List<T> القياسية في كوتلن غير مستقرة (Unstable) ويعيد رسمها دائماً؟

لأن واجهة List<T> في لغة Kotlin هي واجهة للقراءة فقط ولكن يمكن أن يكون الكائن الفعلي خلفها في وقت التشغيل قائمة قابلة للتعديل مثل ArrayList أو MutableList! وبما أن مترجم Compose لا يملك ضماناً في وقت الترجمة بأن عناصر القائمة لم تتغير من مكان آخر بدون تغيير المرجع، فإنه يصنفها كـ Unstable ولا يتخطى إعادة تركيب الدالة إلا إذا استخدمت ImmutableList أو غلفتها بكلاس يحمل وسم @Immutable أو فعلت ميزة Strong Skipping Mode.

ما الفرق الهندسي بين remember(key) وderivedStateOf ومتى أستخدم كلاً منهما؟

تُستخدم remember(key) عندما تريد إعادة حساب قيمة في كل مرة يتغير فيها المتغير key بالضبط (تتغير المدخلات بنفس وتيرة المخرجات). أما derivedStateOf فتُستخدم عندما تتغير المدخلات بسرعة عالية جداً (مثل إزاحة التمرير في LazyListState كل إطار)، بينما النتيجة المنطقية التي تهم الواجهة (مثل: هل تجاوز المستخدم العنصر الأول true/false) لا تتغير إلا نادراً.

كيف يساعد تأجيل قراءة الحالة (Deferring State Reads) عبر Lambda Modifiers في منع التقطيع أثناء التحريك؟

يمر كل إطار في Compose بثلاث مراحل: التركيب (Composition)، التخطيط (Layout)، ثم الرسم (Drawing). إذا قرأت قيمة متغيرة باستمرار مباشرةً داخل جسم الدالة @Composable، فستجبر النظام على تنفيذ المراحل الثلاث كلها في كل إطار! أما عند تمرير القراءة داخل دالة لامدا مثل Modifier.offset { IntOffset(0, scrollOffset) } أو Modifier.graphicsLayer { alpha = animatedAlpha }، فإن Compose يتخطى مرحلة التركيب تماماً وينفذ التعديل مباشرةً في مرحلة التخطيط أو الرسم.

ما هي ملفات Baseline Profiles وكم تبلغ نسبة تسريعها لتطبيقات Jetpack Compose؟

بما أن Jetpack Compose يتم توزيعه كمكتبة برمجية مع التطبيق وليس جزءاً مدمجاً داخل نظام أندرويد نفسه، فإن مترجم ART يضطر لترجمة دوال Compose في وقت التشغيل (JIT) عند أول فتح للتطبيق. توفر ملفات Baseline Profiles قائمة بالمسارات الحرجة ليقوم متجر Google Play بترجمتها مسبقاً إلى كود آلة أصيل (AOT Compilation) أثناء التثبيت، مما يسرّع إقلاع التطبيق والتمرير بنسبة 30% إلى 40%.
