الدليل الهندسي لمعمارية MVI (Model-View-Intent) في Kotlin Multiplatform: كيف تدير حالة الواجهة (UI State) والأحداث الجانبية بدون أخطاء تزامن؟

تاريخ النشر: 08 نوفمبر 2026 - التصنيف: برمجة وتطوير - تطوير الهواتف والأنظمة المتعددة

عندما يكبر حجم تطبيقك المبني بـ Kotlin Multiplatform (KMP) وواجهات Compose Multiplatform، تبدأ المشاكل الخفية بالظهور في الشاشات المعقدة: مؤشر تحميل يظل عالقاً على الشاشة رغم ظهور البيانات، أو رسالة خطأ تنبثق مرتين عند تدوير الهاتف، أو تعارض في حالة سلة المشتريات عندما يضغط المستخدم على زرّين بسرعة! السبب الجذري لهذه الأعطال ليس في إطار العمل، بل في تشتت حالة الواجهة عبر متغيرات متعددة قابلة للتعديل المتزامن.

في هذا الدليل الهندسي العميق من مدونة كونكت تاق، نشرح كيف تعالج معمارية MVI (Model-View-Intent) هذه المعضلة جذرياً عبر فرض حلقة تدفق البيانات أحادي الاتجاه (Unidirectional Data Flow — UDF)، وكيف طوّرنا في شركة كونكت تاق حزمة مكتباتنا المعمارية مفتوحة المصدر (mvi-lib-kmp، وresult-lib-kmp، وactions-lib-kmp) المتاحة في قسم المكاتب البرمجية لتوحيد إدارة الحالة في أكثر من 31 تطبيقاً تجارياً وخدمياً.

خلاصة تنفيذية لمهندسي البرمجيات ومطوري KMP
  • معادلة الواجهة التصريحية: في Compose، الواجهة هي دالة رياضية صافية للحالة UI = f(State)؛ ومعمارية MVI تضمن وجود كائن حالة واحد فقط غير قابل للتعديل (Single Immutable UiState) لكل شاشة.
  • التحديث الذري الآمن (Atomic State Mutation): يُمنع تعديل الحالة عبر _state.value = ... في العمليات المتوازية؛ بل يُستخدم _state.update { it.copy(...) } القائم على خوارزمية Compare-And-Swap (CAS) لمنع ضياع التحديثات.
  • فصل الحالة المستمرة عن الحدث العابر: تُبث الحالة المستمرة عبر StateFlow، بينما تُرسل الأحداث لمرة واحدة (One-Time Side Effects كالتنقل والرسائل العابرة) عبر Channel(Channel.BUFFERED).
  • مكتبات كونكت تاق الجاهزة: يمكنك اختصار مئات الأسطر المتكررة عبر استخدام مكتبات mvi-lib-kmp وresult-lib-kmp وcoroutine-dispatchers-kmp مباشرةً في مشروعك.

1. تشريح حلقة MVI: كيف يدور التدفق أحادي الاتجاه بين Intent وModel وView؟

تستمد معمارية MVI فلسفتها من البرمجة التفاعلية الوظيفية (Functional Reactive Programming)، حيث تتدفق البيانات في دائرة مغلقة ذات اتجاه واحد لا يمكن كسره (راجع أيضاً دليل Compose Multiplatform لبناء واجهات مشتركة ودليل Jetpack Compose الحديث):

  1. النية / الإجراء (Intent / Action): لا تعني كلمة Intent هنا كائن android.content.Intent الخاص بنظام أندرويد، بل تعني «نية المستخدم أو الحدث الوارد من الواجهة» (مثل: الضغط على زر البحث، تغيير نص حقل الإدخال، أو سحب الشاشة للتحديث).
  2. النموذج / المُخفِّض (Model / Reducer): يستقبل الـ ViewModel النية، ينفذ منطق الأعمال غير المتزامن عبر UseCases وRepositories، ثم يدمج النتيجة مع الحالة السابقة لإنتاج كائن حالة جديد كلياً غير قابل للتعديل (New Immutable Model/State).
  3. الواجهة المرئية (View / Composable): تراقب دالة @Composable تدفق الحالة (StateFlow) فقط وتعيد رسم الأجزاء التي تغيّرت دون أن تمتلك أي صلاحية لتعديل الحالة مباشرةً من داخل الواجهة.

2. المقارنة الهندسية: لماذا تتفوق MVI على MVVM التقليدية في واجهات Compose؟

يوضح الجدول الهندسي التالي الفوارق الجوهرية بين نمط MVVM التقليدي متعدد التدفقات ونمط MVI الموحد في المشاريع الكبيرة:

معيار المقارنة المعماري نمط MVVM التقليدي (Multiple Streams) نمط MVI الحديث (Single State + UDF)
تمثيل حالة الشاشة موزع بين عدة متغيرات (loadingFlow, dataFlow, errorFlow) كائن واحد شامل غير قابل للتعديل (data class UiState)
خطر تضارب الحالات (State Inconsistency) مرتفع — قد تظهر حالة التحميل والخطأ معاً إذا لم تُصفَّر يدوياً منعدم — انتقال الحالة ذري ومحصور عبر update {}
نقطة دخول أوامر الواجهة عشرات الدوال العامة المتفرقة داخل الـ ViewModel بوابة واحدة موحدة (fun onIntent(intent: Intent)) يسهل تسجيلها واختبارها
تتبع الأخطاء (Crash Reproduction) صعب — يتطلب معرفة ترتيب استدعاء عدة دوال متداخلة سهل جداً — يكفي تسجيل آخر UiState وآخر Intent لإعادة تمثيل العطل

3. العقد الثلاثي (Contract): كيف تصمم State وIntent وSideEffect باحترافية؟

أفضل ممارسة هندسية في مشاريع Kotlin Multiplatform هي تجميع عناصر الشاشة الثلاثة داخل ملف عقد واضح (ScreenContract.kt) بحيث يفهم أي مطور في الفريق كل ما تفعله الشاشة بمجرد قراءة هذا الملف:

1. تعريف العقد الثلاثي للشاشة (State, Intent, SideEffect) بلغة Kotlin 
// 1. الحالة المستمرة للشاشة (Immutable UI State)
data class ProductsUiState(
    val query: String = "",
    val isLoading: Boolean = false,
    val products: List<ProductItem> = emptyList(),
    val errorBannerMessage: String? = null
)

// 2. نوايا وأفعال المستخدم (User Intents)
sealed interface ProductsIntent {
    data class SearchQueryChanged(val query: String) : ProductsIntent
    data object RefreshClicked : ProductsIntent
    data class ProductClicked(val productId: String) : ProductsIntent
}

// 3. الآثار الجانبية العابرة لمرة واحدة (One-Time Side Effects)
sealed interface ProductsEffect {
    data class NavigateToDetails(val productId: String) : ProductsEffect
    data class ShowToast(val message: String) : ProductsEffect
}

4. التطبيق الكودي الكامل: بناء MviViewModel متين مقاوم لأخطاء التزامن

الآن نربط هذا العقد الثلاثي داخل قاعدة BaseMviViewModel (المتوفر جاهزاً في مكتبتنا mvi-lib-kmp)، مع استخدام StateFlow.update {} لتحديث الحالة بأمان تزامني، وChannel(Channel.BUFFERED) لإرسال الآثار الجانبية العابرة دون فقدانها:

2. تطبيق الـ ViewModel واستهلاك الحالة والأثر الجانبي بأمان في Compose 
class ProductsViewModel(
    private val searchProductsUseCase: SearchProductsUseCase
) : ViewModel() {

    private val _state = MutableStateFlow(ProductsUiState())
    val state: StateFlow<ProductsUiState> = _state.asStateFlow()

    private val _effect = Channel<ProductsEffect>(Channel.BUFFERED)
    val effect: Flow<ProductsEffect> = _effect.receiveAsFlow()

    fun onIntent(intent: ProductsIntent) {
        when (intent) {
            is ProductsIntent.SearchQueryChanged => {
                // تحديث ذري آمن ضد أخطاء التزامن (CAS Atomic Update)
                _state.update { it.copy(query = intent.query, errorBannerMessage = null) }
            }
            is ProductsIntent.RefreshClicked => loadProducts()
            is ProductsIntent.ProductClicked => {
                viewModelScope.launch {
                    _effect.send(ProductsEffect.NavigateToDetails(intent.productId))
                }
            }
        }
    }

    private fun loadProducts() {
        viewModelScope.launch {
            _state.update { it.copy(isLoading = true, errorBannerMessage = null) }
            searchProductsUseCase(_state.value.query)
                .onSuccess { items =>
                    _state.update { it.copy(isLoading = false, products = items) }
                }
                .onFailure { error =>
                    _state.update { it.copy(isLoading = false, errorBannerMessage = error.message) }
                    _effect.send(ProductsEffect.ShowToast("تعذر تحديث القائمة"))
                }
        }
    }
}

5. معالجة الأخطاء وتنسيق المعمارية عبر مكتبات mvi-lib-kmp وresult-lib-kmp

لتجنب إعادة كتابة قوالب الـ MVI في كل مشروع جديد، قمنا في شركة كونكت تاق بتجريد هذه المعمارية في حزمة مكتبات معيارية مفتوحة المصدر متاحة للمطورين في صفحة المكاتب البرمجية (ويمكنك دمجها مع طبقة التخزين المشروحة في دليل إدارة البيانات في KMP عبر Room وDataStore):

  • مكتبة mvi-lib-kmp: توفر صنف الأساس MviViewModel<State, Intent, Effect> جاهزاً مع أنابيب معالجة النوايا (Coroutine Pipelines) وقوالب UseCase المعيارية.
  • مكتبة result-lib-kmp وcommon-models: توفر مغلف نتائج آمن نوعياً (Type-safe Result & DomainError) يمنع تسرب الاستثناءات غير المتوقعة (Uncaught Exceptions) من طبقة الشبكة أو قاعدة البيانات إلى طبقة الواجهة.
  • مكتبة actions-lib-kmp: توفر ناقل أحداث وإجراءات مفكك الارتباط (Universal Action Bus) للتنسيق الآمن بين الوحدات المستقلة (Multi-Module KMP Features).
  • مكتبة coroutine-dispatchers-kmp: توفر واجهة DispatcherProvider قابلة للحقن لتبديل موزعات الخيوط (IO, Default, Main) بموزع اختبار فوري (StandardTestDispatcher) أثناء اختبارات الوحدة.

6. الأسئلة الشائعة حول معمارية MVI وإدارة الحالة في KMP

لماذا تتفوق معمارية MVI على MVVM التقليدية عند بناء واجهات Jetpack Compose وCompose Multiplatform؟

في معمارية MVVM التقليدية، غالباً ما يمتلك الـ ViewModel عدة تدفقات حالة منفصلة (مثل isLoading وerrorMessage وitemsList)، مما قد يولّد حالات متناقضة عند تحديثها من خيوط متزامنة (مثل ظهور مؤشر التحميل ورسالة الخطأ في نفس اللحظة). أما معمارية MVI فتفرض مصدر حقيقة واحداً غير قابل للتعديل (Single Immutable UiState) يتم تحديثه ذرياً عبر الدالة update {}، مما يطابق طبيعة إعادة التركيب (Recomposition) في Compose بنسبة 100%.

ما الفرق بين State (الحالة) وSideEffect (الأثر الجانبي لمرة واحدة) في معمارية MVI؟

تمثل الحالة (UiState) ما يجب رسمه على الشاشة بشكل مستمر حتى عند تدوير الجهاز أو إعادة بناء الواجهة (مثل قائمة المنتجات وحالة التحميل)، وتُحفظ داخل StateFlow. أما الأثر الجانبي (SideEffect / Event) فهو حدث عابر يُنفّذ مرة واحدة فقط ولا يجوز تكراره عند تدوير الشاشة (مثل عرض رسالة Snackbar أو الانتقال إلى شاشة الدفع)، ويُرسل عبر Channel مع استهلاكه كـ Flow.

لماذا يجب استخدام MutableStateFlow.update {} بدلاً من إسناد القيمة مباشرة عبر .value = في البيئات المتزامنة؟

إذا كان لديك عمليتان غير متزامنتين (Coroutines) تعملان في نفس الوقت وتستخدمان _state.value = _state.value.copy(...)، فقد تقرأ كلتا العمليتين نفس النسخة القديمة وتكتب إحداهما فوق الأخرى (Lost Update Race Condition). أما الدالة الذرية _state.update { current -> current.copy(...) } فتستخدم حلقة مقارنة وتبديل (CAS — Compare-And-Swap) تضمن عدم ضياع أي تحديث متزامن.

كيف أسهّل اختبار الوحدة (Unit Testing) للـ ViewModel المبني بمعمارية MVI في مشاريع KMP؟

بما أن معمارية MVI تعتمد على مدخل واحد (onIntent) ومخرجين واضحين (state وeffect)، يصبح الاختبار حتمياً وسهلاً للغاية: تحقن مزود موزعات اختباري (TestDispatcherProvider مثل مكتبة coroutine-dispatchers-kmp)، وترسل النية عبر viewModel.onIntent(...)، ثم تتحقق من تسلسل الحالات المتوقعة مباشرةً.
