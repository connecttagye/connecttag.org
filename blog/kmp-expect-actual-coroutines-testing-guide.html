كيف تصمم جسور الأنظمة الأصلية (expect / actual وواجهات Interface Bridges) وتكتب اختبارات وحدات سريعة في Kotlin Multiplatform؟

تاريخ النشر: 08 نوفمبر 2026

يكمن السحر الهندسي الحقيقي لتقنية Kotlin Multiplatform (KMP) (كما أوضحنا في مقارنة KMP مع Flutter) في أنها لا تعزلك داخل آلة افتراضية مغلقة، بل تمنح الكود المشترك في commonMain وصولاً مباشراً وأصيلاً لواجهات النظام في أندرويد (JVM/Android SDK) وأبل (iOS Objective-C / Swift) وسطح المكتب والويب. غير أن أول قرار معماري يواجه أي مهندس عند بناء مشروع KMP ضخم هو: متى أستخدم آلية expect / actual المدمجة في اللغة، ومتى أستخدم الواجهات البرمجية القابلة للحقن (Dependency Injection Interfaces)؟

في هذا الدليل الهندسي والعملي، نضع بين يديك القواعد المعمارية الصارمة لتصميم جسور الأنظمة الأصلية دون الإضرار بقابلية الاختبار (Testability)، ونشرح كيف تتغلب على مشكلة تجمّد أو فشل اختبارات الكوروتينات عبر حقن DispatcherProvider واستخدام runTest وStandardTestDispatcher ومكتبة Turbine، مع أمثلة حية من مكاتب coroutine-dispatchers-kmp وlogging-lib-kmp وdevice-lib-kmp في قسم المكاتب البرمجية في كونكت تاق.

خلاصة تنفيذية سريعة (Key Takeaways)
  • اجعل Interface خيارك الأول للخدمات ذات الحالة: أي مكون يعتمد على موارد النظام (مثل البلوتوث، قاعدة البيانات، الحافظة، أو الشبكة) ويحتاج إلى محاكاة (Fake/Mock) في الاختبارات يجب أن يُصمم كـ interface في commonMain وليس كـ expect class.
  • استخدم expect / actual للدوال عديمة الحالة وtypealias: تتألق expect fun وactual typealias في ربط الأنواع الأصلية (مثل UUID) أو كتابة مصانع الكائنات (Platform Factories).
  • يُحظر كتابة Dispatchers.IO أو Dispatchers.Main بشكل صلب: استدعاء موزعات الكوروتين مباشرةً داخل ViewModel أو Repository يجعل اختباراتك بطيئة ومتقلبة (Flaky)؛ الحل هو حقن عقد DispatcherProvider.
  • الساعة الافتراضية في runTest تتخطى التأخير الزمني فوراً: دالة delay(30_000) داخل اختبار يستخدم StandardTestDispatcher تنفذ في أقل من 1 ملي ثانية دون انتظار فعلي!

1. تشريح المعمارية الهرمية لمجموعات المصادر (Hierarchical Source Sets) في KMP

ينظم مترجم Kotlin Multiplatform الكود البرمجي في شجرة هرمية من مجموعات المصادر (Source Sets). يقع الكود المشترك بالكامل في قمة الهرم داخل commonMain، بينما تقع الاختبارات المشتركة في commonTest، وتتفرع تحتها المنصات المستهدفة (androidMain، iosMain، jvmMain، wasmJsMain).

عندما يحتاج الكود في commonMain إلى استدعاء قدرة خاصة بنظام التشغيل (مثل قراءة اسم موديل الجهاز، أو الكتابة في سجل النظام Timber / NSLog، أو الوصول للحافظة)، يتيح لك المترجم طريقتين هندسيتين لبناء هذا الجسر:

  1. الربط في وقت الترجمة (Compile-Time Binding) عبر expect / actual: تعلن في commonMain عن توقيع دالة أو كلاس بكلمة expect، ويلزمك المترجم بتقديم تنفيذ actual مطابق له في كل منصة مستهدفة؛ ثم يقوم المترجم باستبدال الاستدعاء مباشرةً أثناء بناء الحزمة الثنائية.
  2. الربط في وقت التشغيل (Runtime Polymorphism) عبر Interfaces + Dependency Injection: تعرّف عقداً برمجياً interface في commonMain، وتكتب كلاساً ينفذه في كل منصة (مثلاً AndroidClipboardBridge الذي يأخذ Context في مُنشئه، وIosClipboardBridge الذي يستخدم UIPasteboard)، ثم تحقنه عبر Koin أو Kotlin-Inject أو يدوياً.

2. المقارنة المعمارية الحاسمة: متى تستخدم expect / actual ومتى تستخدم الواجهات (Interfaces)؟

يوضح الجدول الهندسي التالي متى تختار كلاً من الآليتين وفق أفضل الممارسات المعتمدة من فريق JetBrains:

وجه المقارنة آلية expect / actual الواجهات البرمجية (Interface Bridges)
وقت الربط (Binding Time) ثابت في وقت الترجمة (Compile-Time)؛ تطبيق واحد فقط لكل منصة. مرن في وقت التشغيل (Runtime)؛ يدعم تعدد التطبيقات.
قابلية المحاكاة والاختبار (Testing) صعبة؛ لا يمكن تمرير نسخة وهمية (Fake) بسهولة في commonTest. ممتازة؛ يمكنك تمرير FakeRepository أو FakeDeviceBridge بسطر واحد.
تمرير تبعيات المنصة في المُنشئ مقيد جداً؛ لأن توقيع المُنشئ في expect class لا يعرف كائن Android Context! حر تماماً؛ كل كلاس في androidMain يستقبل Context في مُنشئه الطبيعي.
الاستخدام الهندسي الأمثل actual typealias، الدوال التوسعية عديمة الحالة، ودوال المصنع (Factory Functions). مستودعات البيانات، مديري الحساسات والاتصال، جسور النظام، وخدمات التشفير.

3. هندسة التزامن القابل للاختبار: لماذا يجب حقن DispatcherProvider بدلاً من Dispatchers المباشرة؟

من أكثر الأخطاء شيوعاً في مشاريع KMP كتابة withContext(Dispatchers.IO) أو إطلاق كوروتين على Dispatchers.Default مباشرةً داخل طبقات منطق الأعمال. عندما تحاول كتابة اختبار وحدات لهذا الكود في commonTest، ستفاجأ بأن الاختبار يفشل لأن الكوروتين يعمل في خيط منفصل خارج سيطرة جدولة الاختبار!

الحل المعماري النظيف (الذي تطبقه مكتبة coroutine-dispatchers-kmp) هو تعريف عقد DispatcherProvider وحقنه في جميع الكلاسات:

// 1. In commonMain: Injectable DispatcherProvider Contract
interface DispatcherProvider {
    val main: CoroutineDispatcher
    val io: CoroutineDispatcher
    val default: CoroutineDispatcher
    val unconfined: CoroutineDispatcher
}

// 2. Production Implementation (Injected via DI in app launch)
class DefaultDispatcherProvider : DispatcherProvider {
    override val main: CoroutineDispatcher = Dispatchers.Main
    override val io: CoroutineDispatcher = Dispatchers.IO
    override val default: CoroutineDispatcher = Dispatchers.Default
    override val unconfined: CoroutineDispatcher = Dispatchers.Unconfined
}

// 3. Test Implementation (Used in commonTest with a single TestDispatcher)
class TestDispatcherProvider(
    val testDispatcher: TestDispatcher = StandardTestDispatcher()
) : DispatcherProvider {
    override val main: CoroutineDispatcher = testDispatcher
    override val io: CoroutineDispatcher = testDispatcher
    override val default: CoroutineDispatcher = testDispatcher
    override val unconfined: CoroutineDispatcher = testDispatcher
}

4. كتابة اختبارات وحدات حتمية لتدفقات StateFlow عبر runTest وTurbine في commonTest

بفضل حقن DispatcherProvider وبناء الواجهات على نمط معمارية MVI أحادية التدفق، يمكنك الآن اختبار أي ViewModel أو UseCase في commonTest والتحقق من تتابع حالات الواجهة (Loading → Success / Error) في أقل من 5 ملي ثانية:

import kotlinx.coroutines.test.StandardTestDispatcher
import kotlinx.coroutines.test.advanceUntilIdle
import kotlinx.coroutines.test.runTest
import kotlin.test.Test
import kotlin.test.assertEquals
import kotlin.test.assertFalse
import kotlin.test.assertTrue

class DeviceScannerViewModelTest {

    @Test
    fun whenScanTriggered_emitsLoadingThenDeviceListDeterministically() = runTest {
        // Arrange: Share the same TestScheduler with our TestDispatcherProvider
        val testDispatcher = StandardTestDispatcher(testScheduler)
        val dispatchers = TestDispatcherProvider(testDispatcher)
        val fakeBridge = FakeDeviceDiagnosticsBridge(
            mockBatteryLevel = 92,
            mockModelName = "ConnectTag-Pro"
        )
        val viewModel = DeviceScannerViewModel(
            deviceBridge = fakeBridge,
            dispatchers = dispatchers
        )

        // Act: Dispatch user intent
        viewModel.onIntent(ScannerIntent.StartHardwareCheck)

        // Advance virtual time until all queued coroutines complete
        advanceUntilIdle()

        // Assert: Verify final immutable UI state
        val state = viewModel.uiState.value
        assertFalse(state.isScanning)
        assertEquals(92, state.batteryPercentage)
        assertTrue(state.isHealthy)
    }
}

مكاتب جسور الأنظمة واختبار الكوروتينات في كونكت تاق:

  • مكتبة coroutine-dispatchers-kmp في قسم المكاتب البرمجية: توفر عقود DispatcherProvider القابلة للحقن وموزعات الاختبار الجاهزة لفصل منطق الأعمال عن خيوط النظام.

6. الأسئلة الشائعة والمصادر الهندسية المعتمدة

لماذا ينصح فريق JetBrains بتفضيل الواجهات البرمجية (Interfaces) على expect class في منطق الأعمال داخل KMP؟

لأن آلية expect / actual تربط الكود بتطبيق واحد ثابت في وقت الترجمة (Compile-Time Binding)، مما يجعل استبدال الكلاس بنسخة وهمية (Fake) أثناء اختبارات الوحدات في commonTest أمراً عسيراً، كما يمنع تمرير تبعيات مثل Android Context في المُنشئ بسهولة. أما الواجهات البرمجية (Interfaces) فتسمح بحقن تطبيق حقيقي لكل منصة في الإنتاج وتطبيق مزيف خفيف في الاختبارات.

ما هي الحالات الهندسية التي تتفوق فيها expect / actual على الواجهات البرمجية؟

تتفوق expect / actual في أربع حالات محددة: 1) ربط نوع مشترك بنوع أصيل موجود مسبقاً عبر actual typealias. 2) الدوال التوسعية والعليا البسيطة التي لا تملك حالة داخلية (Stateless Top-Level Functions). 3) توفير دالة مصنع (Factory Function) تنشئ الكائن المناسب للمنصة. 4) تعريف الوسوم (Annotations) الاختيارية الخاصة بالمنصات.

لماذا يفشل اختبار ViewModel في commonTest عند استدعاء Dispatchers.Main أو Dispatchers.IO مباشرةً؟

لأن Dispatchers.Main يعتمد على حلقة أحداث الواجهة الرسومية للنظام، وهي غير موجودة أثناء تشغيل اختبارات الوحدات السريعة! وعند كتابة Dispatchers.IO بشكل صلب داخل الكود، تنتقل المهام إلى خيوط حقيقية خارج سيطرة محرك الاختبار الزمني (TestCoroutineScheduler)، فتفشل الاختبارات بشكل عشوائي. الحل الهندسي هو حقن واجهة DispatcherProvider.

ما الفرق بين StandardTestDispatcher وUnconfinedTestDispatcher في مكتبة kotlinx-coroutines-test؟

يضع StandardTestDispatcher كافة الكوروتينات الجديدة في طابور انتظار افتراضي ولا ينفذها إلا عندما تتقدم الساعة الافتراضية أو تستدعي advanceUntilIdle()، مما يمنحك تحكماً دقيقاً في اختبار حالات التحميل المتعاقبة. بينما ينفذ UnconfinedTestDispatcher الكوروتينات بشكل فوري ومتلهف فور إطلاقها، وهو مناسب لتجمع انبعاثات StateFlow في الخلفية.
